# Ultimate League — 호랑이의 시선 (축구) v2

축구 프리뷰·리뷰 콘텐츠 작성 시스템. **정확도를 측정하고 교정하는 장치**를 붙인 개정판이다.

---

## 왜 v1이 틀렸나

"맨날 틀린다"의 원인은 축구 지식이 아니었다. 프롬프트의 구조에 결함이 5개 있었다.

### 1. 확률을 서사에서 뽑았다 — 가장 큰 원인

v1의 절차는 이랬다.

> 시나리오 A/B/C를 만들고 발생 확률을 배분한다(합 100%). **이 배분이 추정확률의 뼈대다.**

이건 순서가 거꾸로다. 사람은 이야기를 만들 때 무승부를 상상하지 못하고,
최근 결과를 과대평가하며, 자기 결론을 지지하는 정보만 모은다.
그 편향이 그대로 숫자가 된다.

→ **v2는 기대득점 분포에서 확률을 뽑고, 시나리오는 그걸 설명만 한다.**

### 2. 마진 제거 방식이 언더독을 부풀렸다

v1의 `p_raw / sum(p_raw)` (비례 정규화)는 favourite-longshot bias를 보정하지 못한다.
직접 재보면 이렇다.

```
$ python3 tools/devig.py 1x2 1.30 5.20 9.00
오버라운드 107.26%  (마진 7.26%)
shin vs proportional 최대 격차: 2.07%p
→ 방식 차이만으로 이 정도가 벌어진다. 이 크기 이하의 '엣지'는 신호가 아니다.
```

v1의 주력 픽 기준이 "엣지 4%p"였다. **계산 방식만 바꿔도 그 엣지의 절반이 사라진다.**
즉 v1이 잡아낸 엣지 중 상당수는 실제 우위가 아니라 계산 오차였다.

→ **v2는 Shin 방식으로 통일하고, 오버라운드 7% 초과 배당판은 기준에서 뺀다.**

### 3. 무승부를 구조적으로 과소평가했다

v1은 "무승부 확률을 지나치게 낮게 잡지 않았는가(축구 평균 24~28%)"라고 경고만 했을 뿐,
강제 장치가 없었다. 그리고 순수 포아송조차 무승부를 낮게 잡는다.

```
$ python3 tools/poisson.py --lh 1.65 --la 1.10
  (독립 포아송 무승부 24.45% → DC 보정 27.47%)
```

Dixon-Coles 보정 없이는 3%p가 그냥 빠진다. 여기에 서사 편향이 더해지면 격차는 더 벌어진다.

→ **v2는 Dixon-Coles 보정을 기본 적용하고, 리그 베이스레이트 대비 ±6%p 이탈을 검산으로 막는다.**

### 4. 시장을 이기려 들었다

클로징 라인은 공개 정보 기준으로 가장 강한 단일 예측자다.
텍스트 분석이 그걸 통째로 이길 가능성은 낮다.
v1은 시장을 비교 대상으로만 뒀기 때문에, 모델이 시장과 20%p 갈려도 아무 제동이 없었다.

→ **v2는 시장을 기준점으로 삼고, 모델은 이동 폭만 담당한다. 이탈 상한이 있다.**
자유도를 줄이는 것이 정확도를 올리는 가장 확실한 방법이다.

### 5. 측정 장치가 아예 없었다

v1에는 픽 기록도, 적중률 집계도, 캘리브레이션도 없었다.
측정하지 않으면 무엇이 틀렸는지 알 수 없고, 알 수 없으면 고칠 수 없다.
"맨날 틀린다"는 것도 사실은 감각이지 데이터가 아니다.

→ **v2는 PASS를 포함해 모든 픽을 기록하고, 20건마다 Brier·CLV·캘리브레이션을 뽑는다.**

## 구조

```
prompts/
  시스템_호랑이의시선_v2.md          ← 시스템 프롬프트 (v1 대체)
  templates/
    모드A_확률블록_패치.md            ← 기존 템플릿에 이식할 부분만
reference/
  확률_산출_규칙.md                  ← 모드 A 계산의 최종 권위
  리그별_베이스레이트.md              ← λ 기준값, 무승부 검산 기준
  검증_체크리스트.md                  ← 출력 직전 통과 항목
  자주_틀리는_패턴.md                 ← 작성 전 훑는 12개
tools/
  devig.py                          ← Shin 디빅 · 블렌딩 · 엣지
  poisson.py                        ← 기대득점 → 마켓 확률
  calibrate.py                      ← 픽 기록 → 정확도 측정
  fetch_results.py                  ← football-data.co.uk 결과 CSV 다운로드
  baserate.py                       ← 결과 CSV → 베이스레이트 갱신
logs/
  picks.csv                         ← 기록 (헤더만)
  picks_예시.csv                     ← 스키마 예시
```

의존성 없음. Python 3.8 이상이면 그대로 돌아간다.

## 적용 방법

1. **Claude Project 지식에 `prompts/시스템_호랑이의시선_v2.md`를 넣고 기존 v1을 뺀다.**
   `reference/` 4개 파일도 같이 올린다. 시스템 프롬프트가 이 문서들을 참조한다.
2. **기존 `모드A_프리뷰_템플릿_축구.md`는 유지하고**, `templates/모드A_확률블록_패치.md`의
   6개 패치만 이식한다. 섹션 구성과 SEO 규칙은 잘 돌아가고 있으므로 건드리지 않는다.
3. `reference/리그별_베이스레이트.md`의 시드값을 실제 데이터로 갱신한다 (아래 참조).
4. 다음 프리뷰부터 `logs/picks.csv` 기록을 시작한다. **PASS도 기록한다.**

## 사용 예

### 시장 공정확률

```bash
python3 tools/devig.py 1x2 2.10 3.40 3.60
python3 tools/devig.py 2way 1.91 1.95
```

### 모델 확률

```bash
python3 tools/poisson.py --lh 1.65 --la 1.10 --totals 2.5 3.0 --ah -0.75 -1.0
```

### 블렌딩과 엣지

```bash
python3 tools/devig.py edge \
  --odds 2.10 3.40 3.60 \
  --model 0.487 0.275 0.239 \
  --w 0.78 --maxdev 6 --pick 0
```

`--w`는 정보 등급에 따라 A=0.65 / B=0.78 / C=0.88 / D=0.95를 쓴다.

### 정확도 측정 (20건마다)

```bash
python3 tools/calibrate.py logs/picks.csv --split
```

### 베이스레이트 갱신 (시즌마다)

football-data.co.uk는 회원가입도 API 키도 없이 CSV를 그냥 준다.

```bash
python3 tools/fetch_results.py --list                       # 리그·국가 코드 목록

# 유럽 5대 리그, 최근 3시즌
python3 tools/fetch_results.py --div E0 SP1 D1 I1 F1 --seasons 2425 2526 2627 -o results.csv
python3 tools/baserate.py results.csv --by league

# K리그 (한 파일에 전 시즌이 들어 있어 시즌을 거른다)
python3 tools/fetch_results.py --extra KOR -o kleague.csv
python3 tools/baserate.py kleague.csv --season 2025
```

출력값으로 `reference/리그별_베이스레이트.md`를 덮어쓴다.
네트워크가 막혀 있으면 <https://www.football-data.co.uk/data.php>에서 직접 받아도 된다.
`baserate.py`는 `FTHG/FTAG`와 `HG/AG` 두 포맷을 자동 인식한다.

**주의: 여기서 xG는 안 나온다.** λ 조립에 필요한 팀별 90분당 xG는
FBref의 `Share & Export → Get table as CSV`나 Understat에서 따로 받는다.
자세한 건 `reference/리그별_베이스레이트.md` 3-4절.

## 기대치에 대해 솔직하게

이 개정으로 **적중률이 눈에 띄게 오르지는 않는다.** 오르는 것은 두 가지다.

- **확률의 정확도(캘리브레이션).** 55%라고 쓴 것이 실제로 55% 근처에서 맞는다.
  큰 오류(30%p씩 틀리는 것)가 구조적으로 차단되기 때문이다.
- **틀렸을 때 원인을 특정할 수 있는 능력.** λ 조립이 틀린 건지, 정보 등급 판정이 틀린 건지,
  그냥 운이 나빴던 건지가 로그에서 갈린다.

그리고 반대로 **PASS가 늘어난다.** 그건 시스템이 고장난 게 아니라 작동하는 것이다.
v1이 매 경기 픽을 낼 수 있었던 이유는 임계치를 통과했기 때문이 아니라
임계치를 검증할 방법이 없었기 때문이다.

한 가지 더. 30건 이하 표본에서 적중률은 아무것도 말해주지 않는다.
3%p 엣지를 소음과 구분하려면 수백 건이 필요하다.
그 전까지 판단이 옳았는지 알려주는 유일한 지표는 **CLV**이고, 그래서
`closing_odds` 열을 채우는 것이 이 시스템에서 가장 중요한 습관이다.
